# Building a polished Lumo feature

Polish comes from three things: a concrete reference to match, looking at
the real result, and small rounds of fixes after the first version. Follow
these steps in order. Read `CLAUDE.md` first.

## 1. Pin down the reference

- Find out which real product it should feel like ("like the Windows
  Snipping Tool", "like Android 16 quick settings", "like Pixel"). If the
  owner gave screenshots (often in the project files folder), read them.
- If there is no reference, propose one and say which.
- Write down what must match: layout, spacing, sizes, motion, wording,
  behaviour on keyboard and mouse, dark and light theme.

## 2. Write a short spec and get it approved

Before writing code, post a spec of at most about 15 lines:

- what the user sees and does, step by step;
- edge cases: empty, error, offline, very long text, small screen, second
  monitor, Dutch and Russian strings that are longer than English;
- which files and packages change, and the new versions
  (fetch `origin/main` first and take the next free version);
- how it will be tested.

Wait for the owner's go ahead when the feature is new or the reference is
your own guess. A small fix to an existing feature does not need a spec.

## 3. Build it in the house style

- Reuse what exists: look at a similar app or page first and copy its
  structure and components (`data/ui`, `data/shell/m3`, the Settings
  `components/`).
- Colours only from the theme tokens, icons only from Material Symbols,
  Google Sans Flex, Material 3 Expressive motion. No comments in code.
- Every user-visible string goes through the translation domain.

## 4. Look at it

If `scripts/preview-desktop` is available (KVM and `out/rootfs/` present):

1. `scripts/preview-desktop start`, then `apps --qml-only`, `apps` or `sync`.
2. Open the feature with `launch` and drive it with `input` (click, key, type).
3. Take a screenshot of every state from the spec with
   `scripts/preview-desktop shot _build/preview/shots/<feature>-<state>.png`,
   in light and dark theme, and read each PNG.
4. Compare with the reference. List what differs, fix it, take new shots.
   Repeat until a picky designer would not see a difference worth naming.

If it is not available (a cloud session has no KVM), say so plainly in the
PR and in your reply, list the states the owner should check, and offer to
run the preview on the owner's computer through Remote Control.

## 5. Make the commit complete

One commit per feature. Check every line that applies:

- [ ] code (QML, C++, CMake install rules, `.desktop`, autostart);
- [ ] version bump in all places listed in `CLAUDE.md` > Versions;
- [ ] `debian/changelog` entry that says what the user gets;
- [ ] `debian/control` dependencies, `preinst`/`postrm` for diversions;
- [ ] `data/whatsnew.json` entry for anything visible;
- [ ] Dutch (`po/nl`) and Russian (`po/ru`) translations for new strings;
- [ ] new Material Symbols in `symbols_map.py` and `symbols.lock`;
- [ ] `docs/` updated (`APPS.md`, `DESKTOP.md` or a page of its own) and the
      README feature list when it is a headline feature;
- [ ] tests: the source test, the binary test and `test-live-rootfs.sh`
      check the new files and versions;
- [ ] licence and copyright file for third-party code or assets.

Commit message: a subject that says what the user gets, with the versions
in brackets, e.g. `Quick Share with Android phones (kernora-apps 1.1.45)`.
The body explains why and any non-obvious choice, in plain sentences.
No Claude attribution: no "Generated by Claude Code" footer and no
`Co-Authored-By` or `Claude-Session` trailers, in commits, PRs, issues or
comments.

## 6. Verify before the PR

Run, and show the result in the PR:

```sh
tests/lint-layout.sh
tests/test-kernora-apps-source.sh
tests/test-kernora-desktop-source.sh
```

Run the binary build and test too when a build root is available. Rebase on
`origin/main` right before pushing and check the version is still free.

In the PR: what the user gets, the reference, the screenshots (or the
states still to check), the tests that ran and what did not run.

## 7. Polish round

After the owner tries it, expect a short list ("too busy", "keeps nagging",
"jumps when it opens"). Fix each point as its own small commit, starting with
`fix:` and naming the visible result, e.g. `fix: quick share stops nagging`.
